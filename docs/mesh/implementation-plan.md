# Wick Mesh — Architecture & Implementation Plan
Status: Draft / proposed architecture | 2026-11-26

## 1. Goals
Optional independently versioned Wick stack. Each node is a complete standalone Wick installation (Termux, VPS, desktop). Selective bidirectional replication, distributed execution and per-job orchestration. HP can be offline indefinitely; accepted remote jobs continue without HP. No mandatory permanent master. Aggregate throughput, not transparent pooled RAM/CPU.

## 2. Architecture
- Core: stable mutation hooks, transactional outbox, schema registry, scoped data APIs, durable execution/checkpoint interfaces.
- Mesh stack: authenticated transport, node registry, sync engine, compatibility adapters, coordination, scheduler, worker runtime, LLM router, result aggregation, observability.
- Mesh connector: exposed operations and SDK; Mesh tool: HTML dashboard for pairing, scopes, conflicts, roles, version and jobs.
- Background lifecycle independent of UI and chat; standalone Wick remains usable when Mesh disabled.
- Audit actual develop repository before choosing paths, runtime or dependencies. No implementation assumed.

## 3. Node roles and network
Configurable per node: orchestration, worker, failover, sync, coordination voter; capability tags, priority, resource quotas and permitted connectors. Roles can overlap. Per-job orchestrator selected by load, locality, capabilities, model availability, compatibility and policy. HP default sync-only, no orchestration/worker/voting on mobile data; explicit local execution remains possible. User can opt in. Wi-Fi full sync, mobile manual/on-demand text/metadata, optional tables, no images/attachments/builds by default. Compression, byte budgets, resumable chunks, lazy media, metered network detection with manual override. No worker traffic routed through HP.

## 4. Selective sync
Checklist per category and individual resource, direction (both/push/pull), network and schedule:
- Sessions/messages, projects, memory, agents, skills/prompts, attachments.
- Datatables (individual tables), workflows, schedules, job status/history, image cache.
- Plugins (manifest/version/config), connector instances and settings, optional credentials and browser sessions.
- Users/permissions, tags, AI providers, app settings.
- Host policies, environment variables, logs and secrets excluded by default; device-bound paths/ADB/browser state local. Explicit authorization for sensitive scopes; no privilege escalation through replication.
Initial pairing requires preview of existing overlap, identity mapping, dry-run and backup; never overwrite entire live SQLite database.

## 5. Replication protocol
State-based delta for mutable records; append-only event sync for messages, transactions and audit/history. Transactional outbox captures changes atomically with writes. Stable global IDs plus origin mapping and domain-specific natural keys; detect duplicate pre-existing records without blind merge. Per-field revisions, causal/version vectors, hybrid logical clocks and deterministic tie-break. Compact repeated edits into latest state plus causal metadata; preserve necessary events and tombstones. Per-peer scope checkpoints, idempotent apply, ACK only after durable commit, loop prevention. Hash/Merkle comparison and consistent paginated snapshot with watermark for long-offline nodes; replay changes after watermark. Tombstone retention and rebootstrap rules prevent resurrection even after compaction. Never discard unsynced local changes. Blob content hashes, dedup, chunk resume. Prioritize metadata/chat then tables then media; UI usable while syncing.
Conflict policies per scope: smart field merge, manual, preferred node, last-write-wins (logical clock); retain both conflicting values/audit where necessary. Financial immutable transactions and permissions require domain-specific rules, not blind LWW. Delete-vs-edit explicit policy. Unknown fields preserved or scope blocked. Test convergence under reordered/duplicate delivery and partitions.

## 6. Versions
Independent core, agent, connector, tool, Mesh stack, wire protocol, per-scope schema/adapter and data revision. Handshake advertises supported protocol ranges, schemas, operations and capabilities. Negotiate per scope; compatible scopes continue, incompatible changes queued/quarantined with visible reason. No silent truncation of unknown fields. Migration adapters with round-trip tests, additive schemas first, backup and compatibility gates. Rolling/strict/independent/manual update policies; signed artifacts, pinned commits, health checks, platform-specific builds (Termux ARM64 vs VPS Linux), rollback only if data schema compatible or restore tested backup. Cross-build feasibility must be tested. No automatic deployment merely because a new commit exists unless opted in.

## 7. Distributed orchestration
Job submitted with stable idempotency key and durable acceptance on server before HP disconnects. Persist plan, task DAG, input refs, state, checkpoints and results on durable replicated control plane. One active owner per job, not one permanent orchestrator for all jobs. Eligible VPS nodes can orchestrate different jobs simultaneously and work for each other. Use consensus-backed ownership/leases with monotonic fencing tokens; workers and state stores reject stale owners. Quorum voters should be stable VPS nodes (e.g. 3 voters tolerate 1 failure); two voters cannot guarantee both partition safety and automatic failover. Without quorum pause coordinated claims/schedules, allow standalone local work only where safe. HP excluded by default. Evaluate embedded Raft vs external coordination service; no custom unsafe election. Heartbeat, lease expiry, checkpoint recovery, bounded retry/backoff, dead-letter queue, cancellation, timeout, progress and audit. At-least-once delivery; idempotent operations, dedup keys and external side-effect reconciliation; no blanket exactly-once promise. Schedule occurrence key prevents duplicate claims. Jobs pinned to device (ADB) wait for device.

## 8. Connector SDK and OLX example
Connector declares split/execute/reduce, input schema, capabilities, idempotency, checkpoint and retry semantics. Scheduler deterministically partitions independent tasks, assigns batches by capacity, work stealing and backpressure. Existing opaque operations can run remotely but cannot be automatically parallelized safely.
Example: discover OLX listing IDs, deduplicate, enqueue batches of 100; up to 8 eligible workers claim batches, validate details/cache images, persist per-listing outcomes, aggregate counts and merge into datatable. Use stable IDs rather than unstable page offsets; pagination only parallel where supported. Global per-site/account rate limits and permitted access; honor service restrictions, no bypass. Requeue incomplete batches on failure; checkpoint individual items. Test two workers then five/eight. Similar adapters for House Hunt, Finance review and build jobs. Performance depends on parallel fraction, external limits and overhead.
Illustrative SDK: mesh.submit({operation:'olx.validate_listing', itemsRef, batchSize:100, maxNodes:8, retryPolicy, idempotencyKey}); not an existing API.

## 9. LLM and agents
LLM plans complex goals; connector defines safe splitting; deterministic scheduler assigns work. Hybrid mode: remote orchestrator LLM, optional sub-agents with scoped context, ordinary code workers without LLM for HTTP/parsing/build. Each node advertises providers/models and permitted credential access; route by capabilities, cost, rate limit, privacy and user policy. Shared provider budgets and token accounting; fallback only to approved compatible models. Persist plan/tool results and resumable agent checkpoints, not hidden model reasoning. Aggregate structured outputs and final report on VPS. HP can disconnect after acceptance; no dependence on its provider. External side effects gated by permissions and approvals.

## 10. Security
Mutual authenticated encrypted transport, expiring single-use pairing tokens, node identity keys, revocation and rotation, scoped ACLs, signed/versioned manifests, replay protection, audit, encryption at rest for secrets. Never replicate plaintext credentials by default. Validate remote inputs; remote terminal/build privileges explicitly scoped. Threat model compromised peer, stale owner, malicious payload, secret leakage and resource abuse.

## 11. Dashboard
Nodes: online/heartbeat, roles, CPU/RAM/GPU/storage, versions, capabilities. Sync: checklist, per-resource direction/network policy, preview, bytes, lag, checkpoints, manual pause/resume. Jobs: owner, workers, DAG, progress, retries, cancellation. Conflict center: diff, resolve, audit. Version manager: compatibility, update policy, artifacts, rollback. Network: data usage and budgets. Alerts and structured logs.

## 12. Implementation phases
0. Audit develop: DB engines/migrations, write paths, plugin manifests/lifecycle, scheduler, agent state, provider routing, host access, transport, deployment. Produce ADRs and threat model.
1. Optional Mesh stack skeleton, pairing, discovery, capability negotiation, dashboard, secure remote execution (two nodes).
2. Durable queue, per-job orchestration, consensus-backed leases/fencing, checkpoints, retry, idempotency and remote agent continuation.
3. Connector SDK split/execute/reduce; OLX/House Hunt pilot with 2 then 5 workers, global limits and benchmarks.
4. Selective sync pilot datatables and sessions; transactional outbox, state compaction, snapshots, conflict review; expand adapters.
5. Version negotiation/migrations, plugin sync, rolling deployment, low-data policies, media lazy loading.
6. Multi-agent routing, resource balancing, operational hardening and documentation.
Each phase: feature branch, tests, PR to develop, review, merge/build/install only when authorized; feature flags and rollback. Keep existing standalone behavior.

## 13. Acceptance tests
- HP submits job, receives durable ACK, powers off; VPS completes and reports after reconnect.
- Two nodes process same OLX operation without duplicate final records; worker killed mid-batch resumes.
- Orchestrator killed; eligible VPS takes over from checkpoint; partition/stale owner cannot double-claim.
- Five nodes show measured throughput vs one; report rate-limit and coordination overhead.
- HP offline 21 days and 6 months; repeated edits compact to latest state; messages/history retained; snapshot recovery and deletion convergence.
- Concurrent field edits merge, same-field conflict policy applied, duplicate initial records reviewed.
- Mixed Wick/schema versions sync compatible scopes, queue incompatible ones, preserve unknown fields.
- Mobile data policy blocks bulk media and background worker traffic; measure bytes and resume.
- Revoked peer denied; credentials and host policies excluded by default; standalone operation unaffected.
- Backup/restore, rolling update, migration and rollback tested on Termux and VPS.

## 14. Open decisions
Actual source architecture and extension points unverified; coordination backend, storage model, protocol, retention, default conflict policies, trust model, platform build pipeline and benchmarks require audit. Proposed defaults: optional stack, per-job dynamic orchestration, VPS-only coordination by default, hybrid LLM, state/event hybrid replication, smart merge with configurable LWW, low-data HP. No implementation or deployment performed by this plan.

## 15. Revision — Plugin-first architecture (supersedes conflicting placement/defaults above)
Keep almost all Mesh code, configuration, migrations, UI, transport, coordination, worker/scheduler, LLM routing, sync adapters and policies in an independently installable Wick Mesh plugin/stack. Core changes only for missing stable generic hooks: transactional change feed, authorized data APIs, durable background lifecycle, execution/checkpoint and secure host capabilities. Reuse existing interfaces first; never bypass authorization or write live core DB directly. Audit actual plugin lifecycle and runtime before deciding packaging; if background daemon is necessary, package/manage it with the plugin using supported lifecycle hooks. Separate plugin-owned state and migrations from core DB. Prefer one installable bundle with connector, HTML tool and runtime components where supported. No mandatory core rebuild for routine Mesh changes. Versioned SDK and capability negotiation; independent signed releases, staged update, drain/checkpoint, restart plugin only where supported, rollback with schema compatibility and backup. Test old core/new plugin and new core/old plugin. Keep core PRs minimal and generic, develop branch. Do not claim hot reload until verified.

## 16. Simple setup and configuration UX
Pair via expiring token/QR, choose Full, Mobile, Worker, Backup or Custom profile, select categories, review permissions and apply. Presets editable; node groups inherit policy with per-node overrides. Roles independent from replication. Worker can orchestrate if explicitly enabled; mobile defaults to no worker/orchestration/voting. Advanced settings expose direction, scopes, conflict policy, bandwidth, replication targets, version policy, failover and resource limits. Show effective configuration, inheritance source, dry-run, pending incompatibilities and audit. Store Mesh configuration in plugin-owned versioned schema; device identity, private keys and local overrides never blindly replicated. Group policy changes authenticated and versioned. No duplicate configuration UI for existing Wick plugin settings.

## 17. Existing Wick plugin configuration replication
Replicate existing manifest/version/install intent, enabled status, connector instances, plugin settings, OAuth scope declarations, enabled operations, operation permissions, user/tag access, workflow/schedule definitions and account metadata through supported APIs. Preserve existing Wick UI and semantics. Separate desired shared configuration from device-specific effective state. Stable identity mapping for users/tags/accounts/connectors. Scope declaration does not grant provider consent; tokens may require reauthorization. Credentials/tokens/env/host access policies excluded by default, explicit encrypted opt-in with target approval; never widen privileges automatically. Local executable paths, cache paths and device limits remain local. Remote plugin proxy can expose authorized operations on compatible nodes even without local runtime; optional lightweight UI if supported. Schedule definitions replicated but occurrence claims coordinated to prevent duplicate execution.

## 18. Datatables and file replication
Datatables: per-table checklist, stable IDs, schema, column types, constraints/index definitions, metadata, permissions and rows. Schema changes ordered before dependent records; validate constraints and preserve incompatible changes in quarantine. Incremental row/field deltas, tombstones, snapshots and dedup; no raw live SQLite copying. Modes: full replica, selective replica, on-demand, final committed results only (requires explicit connector result contract), metadata only or disabled. On-demand reads indicate remote availability; offline writes require cached writable scope and conflict handling.
Files: project files, artifacts, attachments, skills, images/cache; temporary files excluded by default. Manifest with stable file ID, logical path, content hash, size, revision, permissions and replica locations. Content-addressed blobs, chunked resumable transfer, hash verification, atomic local materialization, rename without blob retransmission, conflict copies, tombstones and safe garbage collection. Protect against path traversal/symlinks; never expose unauthorized metadata. Virtual file listing and lazy download through supported Wick file APIs; pin offline, Wi-Fi only, metadata only or full download. Explicit replication factor per scope (suggest 2–3 for important data), eligible node placement, repair under-replicated blobs, show actual durability and unavailable files. Replication is not backup; independent snapshots needed.

## 19. Result-only mobile profile
Separate durable job execution state from user-visible result publication. Modes: full selected data, latest state, result only, summary only, on demand, disabled. HP submits job and gets durable ACK; VPS handles orchestration, LLM, retries, checkpoints and intermediate logs. Publish final result envelope (job ID, status, summary, counts, final data refs, artifact refs, revision, errors), idempotently deliver after reconnect. Optional final datatable deltas and file metadata; fetch details/media only on demand. No intermediate traffic to HP by default. Distinguish job result from full table replication; result-only does not guarantee complete offline data. Enforce mobile byte budgets and show pending downloads. No fabricated performance estimates; measure actual bytes.

## 20. Revised delivery and acceptance gates
Phase 0 audit core extension points and prove plugin-only background runtime/update feasibility. Phase 1 plugin skeleton, presets, pairing, versioned config, node groups, secure remote operation. Phase 2 durable orchestration/worker and result-only mobile delivery. Phase 3 connector SDK and distributed pilot. Phase 4 datatable and existing plugin configuration adapters, permissions and conflicts. Phase 5 file manifests/lazy materialization/replica repair, long-offline recovery. Phase 6 compatibility, rolling plugin updates, LLM routing and hardening. Tests: plugin update without core rebuild where supported; config inheritance; no permission escalation or OAuth consent bypass; mixed versions; HP offline completion and result-only byte accounting; datatable schema/row convergence; file rename/dedup/resume, replica loss and offline availability. Keep prior acceptance tests. These are proposed designs, not implemented or source-verified.

## 21. Agreed topology — full server replicas, lightweight HP (supersedes earlier defaults)
Every VPS is a complete Wick installation and defaults to Full Replica of all authorized durable shared scopes, including datatables, project files, artifacts, sessions, plugin configuration, workflows, schedules, job state and retained internal communication. Device-specific runtime files and secrets remain exceptions; secrets require explicit encrypted opt-in. Full replication is eventual, not instantaneous; show per-node lag and readiness. HP remains a standalone Wick installation but defaults to selective/result-only sync, no worker, orchestration or quorum voting. VPS-to-VPS traffic never transits HP. Initial bootstrap previews overlap and storage cost, then snapshots and catches up before marking a node ready. Full replication does not replace independent backup.

## 22. Shared orchestrator and MCP gateway
Default deployment: VPS 1 is preferred active shared orchestrator and MCP ingress; other VPS nodes are workers and eligible standby orchestrators. All server nodes may also execute local tasks. Support centralized, primary/standby, per-job distributed and hierarchical/hybrid modes without changing data model. Primary is a movable role, not a fixed identity. Manual promote, graceful drain/handoff, maintenance transfer and automatic failover require quorum-backed ownership, monotonic fencing and durable checkpoints. A returning former primary rejoins as worker/standby; never reclaim blindly. Overload can delegate jobs to sub-orchestrators under explicit ownership and resource budgets. Without quorum stop coordinated claims; do not promise availability under arbitrary partitions.
Expose a single stable MCP URL via an authenticated HA gateway or supported failover routing; gateway and identity/session continuity must be tested independently of orchestrator election. In-flight MCP calls may disconnect; durable jobs continue and can be queried by stable job ID. GPT connects once to the gateway, not each worker. Global Connector Registry advertises authorized remote operations, node capabilities, schema/version and availability; route by permissions, locality, compatibility, load and optional explicit node selection. Namespace collisions and account mappings must be handled deterministically. Preserve existing wick_search/get/execute/run_code semantics where supported; otherwise expose Mesh connector operations for discovery, remote execute, submit/status/result/cancel and node management. No arbitrary automatic parallelization of opaque operations. Remote calls preserve caller identity, approvals, audit and least privilege; never use gateway service identity to bypass caller ACLs. Long jobs return durable ACK/job ID; no dependence on GPT or HP connection. Plugin-first implementation; audit MCP extension hooks before deciding minimal Core changes.

## 23. HP checklist and local storage lifecycle
Hierarchical checklist by category, individual session, agent, plugin, connector, datatable, project, file and result stream. Expandable advanced policies: full, latest state, result only, summary only, metadata only, on demand, disabled; direction, Wi-Fi/mobile/manual, byte budget, pin offline. Default mobile excludes internal bot traffic, intermediate results, checkpoints, debug logs and bulk media. Show effective scope, estimated bytes where measurable, sync progress, remote/local availability and dependencies (schema/metadata/permissions required for selected data). Unchecking stops future replication; retain local copy by default. Separate Clear Local Copy action with preview/confirmation; never propagate local eviction as global deletion. Protect unsynced local edits before eviction. Rechecking resumes from checkpoint or snapshot. On-demand data requires reachable authorized replica; offline UI clearly marks unavailable content. Preserve existing Wick configuration UI; Mesh only manages replication policies.

## 24. Internal Data Registry — bot/agent communication and runtime state
Audit actual Wick internal directories, database tables, session formats, bot integrations, agent messaging, task queues, execution state and provider checkpoint formats. Do not assume every file under .wick-agent is safe to copy. Plugin-owned versioned registry classifies each logical resource by owner, schema, mutability, sensitivity, durability, sync mode, retention, dependencies, merge strategy and supported API. Unknown internal resources default to local/quarantine until classified. Avoid raw live DB or runtime directory mirroring.
- Durable shared data (full VPS replication by default): chat history, bot/agent/sub-agent messages, task instructions/responses, memory, supported session state, tool call history/results, project files/artifacts, retained audit/debug history subject to redaction and retention. Preserve append-only event IDs, ordering/causal links, correlation IDs, dedup and access control. HP can select these or fetch on demand; default final result only for internal communication.
- Coordinated durable control state: job queue, claims, workflow/schedule occurrences, agent task DAG, checkpoints, retry state, bot delivery receipts and external side-effect ledger. Replicate through consistency-appropriate control-plane mechanisms, not generic last-write-wins file sync. Checkpoint only supported resumable state; provider-specific process memory cannot be assumed portable. Resume from last committed checkpoint or reconcile/retry safely.
- Local-only ephemeral state: PID/socket/lock files, process memory, active browser process/profile locks, temp files, transient caches, local ports and device paths. Never restore a stale lock or running-process marker on another node. Credentials and sensitive session material require separate explicit authorization, encryption and redaction.
- Bot integrations (Slack/Telegram/WhatsApp or others where supported): replicate authorized durable conversation records and configuration, but only the elected/leased consumer for a given account/channel or partition handles incoming events and sends replies. Dedup inbound provider event IDs, persist offsets/receipts, use outbox/idempotency keys when supported, fence stale owners, reconcile ambiguous send outcomes before retry. Do not promise exactly-once delivery when provider lacks idempotency. Failover must not trigger replay of historical messages as new commands. External provider session/device binding and terms must be respected.
Principle: replicate data, coordinate execution. Full replica does not mean every node independently runs identical bots, schedules or workflows. Retention and privacy policies apply across replicas, backups and mobile caches.

## 25. Additional acceptance gates and rollout
Plugin-first remains mandatory design preference. First prove stable MCP gateway/remote execution and role transfer on two nodes; add third coordination voter before claiming single-failure quorum tolerance. Test five full VPS replicas and one lightweight HP; initial sync, lag, mixed versions, storage growth, long-offline HP, result-only traffic and checklist eviction without remote deletion. Test manual primary promotion during active job, crash/partition, gateway reconnect with same URL/job ID, stale owner fencing and standby recovery. Test bot/agent event replication, duplicate inbound events, crash between external send and receipt, checkpoint recovery, no duplicate schedule/bot replies, exclusion of PID/socket/lock/temp files and unknown resources. Measure actual network/storage overhead. All additions are proposed specifications; source audit, runtime feasibility and implementation remain pending.
