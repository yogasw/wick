Browser Network Capture → Replay

Log in once by hand, capture the raw HTTP the browser actually sent, and replay it directly — no cookie-jar bookkeeping, no refresh-token logic. When replay fails, fall back to re-opening the browser.

Problem

Yoga wants to open a browser once — e.g. log in to Facebook manually — capture the full outgoing request(s) the browser made (method, URL, headers, cookies, body) as a list, then replay those directly over plain HTTP going forward. On failure (expired session, 403, redirect-to-login), fall back to opening the browser again to re-capture — the caller never has to reason about cookie rotation or refresh-token mechanics.

This is DevTools' "Copy as cURL" / "Save as HAR" workflow, done programmatically and wired into a connector.

Why this approach

BrowserContext.storageState() only dumps cookies + localStorage — useful for re-authenticating a browser, but the ask is for the raw request, so nothing about which fields matter needs to be understood upfront. Full request capture is ground truth: whatever the browser sent is exactly what gets replayed.

Design

Capture method

Listener page.on("request")

  • Simple, already-vendored playwright-go bindings
  • Gives method / url / headers / postData directly
  • Misses wire-level detail — redirects collapse, some headers are browser-computed

Recommended HAR recording

  • BrowserNewContextOptions.RecordHar — native to Playwright
  • Full fidelity: headers, cookies, timing, redirect chain
  • Industry-standard format — external HAR viewers / curl converters already exist

End-to-end flow

1

session_open (existing op)

Headed live session, HAR recording enabled on the context.

2

Manual interaction

User logs in / clicks through the flow inside the visible browser window.

3

network_capture(session_id, url_filter?) — new op

Stops/flushes HAR recording, parses entries, filters by url_filter if given (else returns XHR/fetch entries, skips static assets). Returns a list of CapturedRequest.

4

Replay

Caller picks the relevant CapturedRequest and fires it via the existing http connector — no browser needed.

5

Retry-fallback on failure

403 / redirect-to-login → caller re-runs session_open + manual login + network_capture, gets a fresh request, retries.

Steps 4–5 are the consumer's responsibility — this connector's job stops at "give me the captured requests." Any workflow/agent wires its own retry policy on top, rather than baking one site's auth logic into the connector.

CapturedRequest shape

type CapturedRequest struct {
    Method  string            `json:"method"`
    URL     string            `json:"url"`
    Headers map[string]string `json:"headers"`
    Cookies string            `json:"cookies"`  // Cookie header, already flattened
    Body    string            `json:"body,omitempty"`
    Status  int               `json:"status"`   // response status, for filtering successful calls
}

Op inputs — network_capture

FieldTypeNotes
session_idstringRequired. From session_open.
url_filterstringOptional substring/regex to narrow returned entries.
include_assetsboolDefault false — skips images/css/font/js.

No new instance-level Config needed — HAR recording toggles per session_open call, not persistent config.

Open questions needs a decision

01 Capture trigger

Does network_capture snapshot "everything since session_open," or do we need a start/stop pair (network_capture_start / network_capture_stop) so the user can bound exactly which interactions get captured?

Leaning: start/stop pair, for precision — costs one extra op

02 Filter defaults

Capture-all-then-filter (simple, but noisy — trackers/analytics pollute the result) vs. require an explicit domain allowlist upfront (cleaner, more setup).

03 Persistence

Requests returned in the tool response only (ephemeral — caller must save them itself), or does the connector also persist to a file under the session dir for later retrieval without re-opening the browser?

04 Replay helper

Build a matching network_replay op in this same connector (fires the CapturedRequest via plain HTTP, still inside this plugin), or leave replay entirely to the generic http connector / caller's own code?

Leaning: leave external — avoids duplicating an HTTP client connector that already exists

Non-goals

  • Solving CSRF / dynamic-token endpoints that can't be statically replayed — caller's job to detect (e.g. a re-auth redirect in the response) and re-capture.
  • TLS/JA3 fingerprint-matching between the captured browser session and the replay client — a real risk raised in discussion, but out of scope here; replay goes over a plain Go http.Client, which won't match Chromium's TLS fingerprint exactly.
